# Диагностика NVLink для TP (nvidia-smi 571.96+, Windows 10)

## 1. Проверка топологии соединений

В новых версиях nvidia-smi команда `topo -m` удалена. Используйте альтернативы:

### 1.1. Проверка состояния линков NVLink

```cmd
nvidia-smi nvlink -s -i 0
nvidia-smi nvlink -s -i 1
```

Каждый линк должен показывать скорость (например `25.781 GB/s`). Если линк неактивен, будет указано `Inactive`.

### 1.2. Проверка возможностей NVLink

```cmd
nvidia-smi nvlink -c -i 0
```

Обратите внимание на:
* **`P2P is supported: true`** — критически важно для распределённых вычислений
* **`Link is supported: true`** — линк активен и доступен

### 1.3. Проверка физического подключения через PCIe

```cmd
nvidia-smi --query-gpu=index,name,pci.bus_id --format=csv -i 0,1
```

GPU с соседними Bus-ID (например `01:00.0` и `03:00.0`) обычно размещены на одной плате и соединены NVLink.

## 2. Мониторинг в реальном времени

### 2.1. Утилиты `watch` недоступны в Windows

В Windows используйте циклический запуск через PowerShell:

```powershell
# Мониторинг состояния NVLink (каждые 2 секунды)
while($true) { nvidia-smi nvlink -s -i 0,1; Clear-Host; Start-Sleep -Seconds 2 }
```

### 2.2. Мониторинг пропускной способности через dmon + GPM

В новых версиях `dmon -s np` заменён на GPM-метрики. NVLink RX/TX — это метрики 60 и 61:

```cmd
nvidia-smi dmon -s u --gpm-metrics=60,61 -d 1 -c 10
```

**Критерии корректной работы:**
1. Столбцы **`nvlrx`** и **`nvltx`** показывают значения в MiB/s, отличные от нуля во время генерации
2. Если оба столбца показывают `0` или `-`, обмен идёт через PCIe, а не NVLink

### 2.3. Мониторинг загрузки GPU

```cmd
nvidia-smi dmon -s u -d 1 -c 10 -i 0,1
```

Столбец **`sm`** (SM Utilization %) показывает загрузку вычислительных ядер.

## 3. Диагностика в Windows 10

### 3.1. Режим TCC (Tesla Compute Cluster)

Проверьте текущий режим:

```cmd
nvidia-smi -q -d COMPUTE | Select-String "Driver Model"
```

Если режим **WDDM**, переведите в TCC (требуются права администратора):

```cmd
nvidia-smi -g 0 -dm 1
nvidia-smi -g 1 -dm 1
```

*После выполнения требуется перезагрузка системы.*

### 3.2. Проверка P2P пропускной способности

Используйте утилиту из CUDA Toolkit:

```cmd
p2pBandwidthLatencyTest.exe
```

**Интерпретация:**
* **> 25–30 Гбайт/с:** Данные передаются через NVLink
* **~10–12 Гбайт/с (PCIe 3.0 x16):** NVLink не используется, обмен через системную шину

### 3.3. Визуальный контроль через Диспетчер задач

Вкладка "Производительность" → GPU:

| Признак | Значение |
|---------|----------|
| `Copy` / `PCIe Link Utilization` постоянно загружены | Обмен через PCIe (некорректно) |
| `Copy` / `PCIe` на нуле, `Compute` загружен синхронно | Обмен через NVLink (корректно) |

## 4. Критическое ограничение Windows: NVLink не используется в llama.cpp

### Диагноз

На Windows NVLink физически активен (`nvidia-smi nvlink -s` показывает скорость линков, P2P поддерживается), но **GPM-метрики NVLink трафика (`nvlrx`/`nvltx`) стабильно равны 0** при работающем распределённом `llama-server`.

**Причина:** На Windows отсутствует NCCL (NVIDIA Collective Communications Library). Библиотека `llama.cpp` использует базовые CUDA P2P-механизмы для обмена между GPU, но в Windows-драйвере CUDA P2P маршрутизируется через **PCIe**, а не через NVLink. Это архитектурное ограничение платформы, а не ошибка конфигурации.

### Решения (по убыванию эффективности)

| Вариант | Описание | Эффект |
|---------|----------|--------|
| **Linux** | Установить Ubuntu/Debian на тот же сервер | NCCL автоматически использует NVLink, полный эффект ускорения |
| **WSL2** | Запустить llama.cpp внутри WSL2 с GPU-поддержкой | NCCL работает, NVLink задействуется |
| **`-sm layer`** | Заменить `-sm row` на `-sm layer` | Меньший объём меж-GPU обмена, снижение зависимости от PCIe |
| **`-sm none`** | Полный дамп на один GPU (`-ts 1,0`) | Нет меж-GPU обмена, но ограничено 32 ГБ VRAM |

### Рекомендация

Для максимальной производительности с NVLink переходите на Linux. На Windows вы ограничены пропускной способностью PCIe (~16 ГБ/с против ~150+ ГБ/с NVLink при 6 линках).
