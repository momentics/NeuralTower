# Тестирование когнитивных возможностей на длинных контекстах

Стенд для оценки удержания контекста, логического мышления и извлечения фактов большими языковыми моделями (на примере **Qwen/Qwen3.6-27B** и квантованных версий). Тестирование адаптировано под **NeuralTower** (4× V100 SXM2 32 ГБ, 128 ГБ HBM2, PCIe 3.0 / SlimSAS, `1Cat-vLLM` / `vLLM`).

---

## 1. Требования к тестированию NeuralTower

### Программные требования

* Установлены `transformers` (токенизация) и `vLLM` / `1Cat-vLLM` с поддержкой Volta (`sm_70`).
* Настроена RoPE (Rotary Position Embedding) для контекстов до 1024K токенов.

```bash
pip install -r requirements.txt
```

---

## 2. Методика и метод тестирования

Вместо классического метода "Needle in a Haystack", проверяющего только память, применяется метод Logical Multi-hop Context Padding.

### Суть метода

1. **Шумовой контекст**: Заполнение реальным фоновым текстом (документация, логи, исходный код) до заданного объёма в токенах.
2. **Целевой фрагмент**: Внедрение в шум микро-задачи со скрытым логическим противоречием или многошаговой зависимостью.
3. **Позиционное сканирование**: Для каждого объёма тест генерируется в трёх позициях для выявления эффекта «потери внимания в середине» (*Lost in the Middle*):
   * Начало (5%)
   * Середина (50%)
   * Конец (95%)

### Сетка тестирования

Тест выполняется строго по возрастанию с шагом (в токенах):

* **2K–16K** — микроконтексты.
* **32K–128K** — базовая зона стабильности.
* **160K–256K** — граница заполнения VRAM.
* **320K–512K** — тяжёлая экстраполяция внимания.
* **640K–1024K** — предел платформы (1 млн токенов).

---

## 3. Процесс работы

Эксперимент разделен на три последовательных этапа:

### Этап 1: Генерация тестов

Скрипт `generate_benchmarks.py` инициализирует токенизатор модели, рассчитывает бюджет токенов для каждой точки сетки, собирает текстовые пакеты с логической задачей в трёх позициях и сохраняет их в JSON в `./neural_tower_dense_benchmarks`.

### Этап 2: Инференс

Управляющий скрипт считывает файлы по возрастанию объёма и отправляет их на API `vLLM`. Логируются ответ модели, TTFT, скорость генерации и утилизация VRAM. При ошибке OOM процесс останавливается, фиксируя предел конфигурации.

### Этап 3: Валидация

Ответы проверяются на соответствие формату JSON и корректность логических выводов (Accuracy / F1).

## 4. Результаты

### Промежуточные результаты (Log-файлы)

В процессе выполнения тестов формируется JSON-массив результатов для каждой точки. Пример структуры записи:

```json
{
  "context_size": "192k",
  "position": "middle",
  "metrics": {
    "ttft_seconds": 14.2,
    "tokens_per_second": 22.4,
    "vram_allocated_gb": 104.5
  },
  "model_response": {
    "conflict_detected": true,
    "root_cause": "NVIDIA driver 580.12 requires 64-bit MMIO base address, but ASUS X99-E WS BIOS forces 32-bit BAR allocation with >2 SXM2 devices active."
  },
  "score": 1.0
}
```

### Финальные результаты

На основе собранных логов строятся три ключевых графика:

1. **Точность (Y: Accuracy, X: Context Size)**: Три линии (начало, середина, конец), показывающие, при каком объёме и в какой позиции модель теряет причинно-следственные связи.
2. **Задержка (Y: TTFT, X: Context Size)**: Масштабируемость фазы Prefill на Volta и влияние обмена через PCIe 3.0.
3. **Физическая ёмкость**: Объём контекста, при котором модель вызывает падение движка по нехватке памяти.
