# Оптимизация среды NeuralTower на базе Gentoo Linux под архитектуру SGLang

Для реализации максимального потенциала связки процессора Xeon E5-2699v4 и четырех ускорителей Tesla V100 (SXM2) в рамках SGLang архитектуры, традиционно выбрана операционная система Gentoo Linux. Настоящий профиль оптимизирован под работу высокоскоростного трехуровневого кэширования SGLang HiCache, алгоритмов инкрементального переиспользования контекста RadixAttention и спекулятивного декодирования EAGLE в гибридной топологии шин NVLink и PCIe 3.0.

## 1. Настройка глобальных параметров сборки (make.conf)

Глубокая пересборка системного окружения с флагами оптимизации под микроархитектуру Broadwell позволяет минимизировать накладные расходы на уровне системных вызовов. Это критически важно для асинхронного планировщика SGLang на базе Triton и uvloop при прокачке ультра-длинного контекста.

Основные параметры в `/etc/portage/make.conf`:

*   `COMMON_FLAGS="-O3 -march=broadwell -pipe -flto=auto"` - применение агрессивной оптимизации и межмодульной оптимизации времени линковки (LTO) для достижения максимальной пропускной способности оперативной памяти.
*   `USE="cuda nccl cudnn mpi tensorrt openmp opencl pcie-p2p numa uvloop -X -wayland -gui -dist-kernel"` - активация поддержки параллельных вычислений, протоколов прямого обмена данными между графическими процессорами (Peer-to-Peer), низкоуровневой оптимизации диспетчеризации NUMA-узлов и высокопроизводительного асинхронного движка событий.
*   `PYTHON_TARGETS="python3_12"` - фиксация стабильной версии интерпретатора, обеспечивающей максимальную скорость работы со скрытыми некопируемыми буферами памяти (`memoryview`).
*   `VIDEO_CARDS="nvidia"` - сборка официального драйвера актуальной ветки 580.x или новее с нативной поддержкой архитектуры Volta (sm_70).

## 2. Низкоуровневая конфигурация ядра Linux 6.x+

Иерархическая структура хранения KV-кэша SGLang (GPU HBM -> CPU RAM -> Intel Optane) требует специфической настройки виртуальной памяти ядра для исключения задержек ввода-вывода (I/O Bottleneck).

Необходимые опции при компиляции ядра (`make menuconfig`):

*   `CONFIG_PCI_P2PDMA=y` - аппаратная поддержка прямого доступа к памяти между устройствами на шине PCIe через коммутаторы PLX без транзита трафика через центральный процессор.
*   `CONFIG_NUMA=y` и `CONFIG_X86_PKG_MULTICORE_IPS=y` - корректная адресация памяти четырехканального режима регистровых модулей ECC DDR4 RDIMM с учетом топологии процессора.
*   `CONFIG_TRANSPARENT_HUGEPAGE=y` и `CONFIG_TRANSPARENT_HUGEPAGE_ALWAYS=y` - принудительное выделение памяти хоста страницами по 2 МБ вместо 4 КБ. Снижает количество промахов кэша процессора (TLB Cache Misses) при мелкоблочном обращении к страницам RadixAttention.
*   `CONFIG_CMA=y` (Contiguous Memory Allocator) - резервирование непрерывных физических областей RAM для ускорения DMA-передачи активаций между мезонинами на стыках слоев конвейерного параллелизма (`PP=2`).
*   `CONFIG_IOSCHED_NONE=y` или `CONFIG_BLK_DEV_THROTTLING=y` - отключение программных планировщиков ввода-вывода операционной системы для накопителя Intel Optane. Для памяти 3D XPoint должен быть жестко выставлен режим `none` (или `kyber`), чтобы сохранить микросекундную латентность при случайном чтении бинарных файлов кэша.

## 3. Системные параметры виртуальной памяти (sysctl.conf)

Для предотвращения деградации шины PCIe из-за нежелательного сброса страниц памяти на системный диск, в файл `/etc/sysctl.conf` необходимо внести следующие директивы подсистемы `vm`:

```ini
# Полностью минимизируем агрессивность использования стандартного Linux Swap
vm.swappiness = 1

# Оптимизируем удержание кэша страниц префиксов в оперативной памяти хоста
vm.vfs_cache_pressure = 50

# Резервирование 48 ГБ под страницы памяти (2MB)
vm.nr_hugepages = 24576
# Резервирование 160 ГБ под страницы памяти (2MB)
#vm.nr_hugepages = 81920
# Резервирование 400 ГБ под страницы памяти (2MB)
#vm.nr_hugepages = 204800

```

## 4. Формирование программного стека машинного обучения

Отказоустойчивость многопользовательской среды и изоляция вычислительных контекстов кодинг-агентов Kilo Code реализуются через сквозную согласованность следующих пакетов:

1.  **Драйверы и инструментарий:** `x11-drivers/nvidia-drivers` (версии 580+) и `dev-util/nvidia-cuda-toolkit:12`. При установке драйверов в чистом headless-режиме (без X-сервера) гарантируется монопольное владение CUDA-драйвера индексами устройств `0,1,2,3` для Tesla V100.
2.  **Библиотеки аппаратного ускорения:** `sci-libs/cudnn:9.x` и `sci-libs/nccl:2.20+`. Сборка NCCL с флагом `pcie-p2p` изолирует All-Reduce трафик тензорного параллелизма (`TP=2`) строго внутри быстрых NVLink-линий мезонинов. При использовании SGLang Triton JIT-ядра требуются дополнительные настройки NUMA-привязки для оптимальной производительности.
3.  **Контейнеризация и среда выполнения:** `app-containers/docker` совместно с `app-containers/nvidia-container-toolkit`. Обеспечивает сквозной проброс скомпилированных Triton-ядер из хост-системы внутрь изолированного окружения SGLang.

## 5. Обновление и запуск системы

После применения конфигурации выполняется полная пересборка дерева пакетов:
`emerge --ask --verbose --update --deep --newuse @world`

Запуск Production-контейнера SGLang в Gentoo выполняется с явным указанием утилиты распределения памяти NUMA для равномерного распределения нагрузки по всем модулям памяти:
`numactl --interleave=all docker compose up -d`
